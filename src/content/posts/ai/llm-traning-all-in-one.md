前阵子准备一个 AI Infra 方向的面试，把大模型推理和训练的工程链路从头到尾捋了一遍。捋完发现一件事：这些听起来很唬人的术语——PD 分离、PagedAttention、ZeRO、Ring AllReduce——单看像一堆互不相干的黑话，但只要抓住三个物理约束，它们就全串起来了。

这三堵墙是：**算力、显存、带宽**。几乎所有 LLM 系统的工程设计，本质都是在和这三样东西讨价还价。

这篇就按这个思路，把推理和训练两条线一次讲清。前半段讲推理，从「一次推理到底发生了什么」开始，顺着 KV Cache 这条主线，一路推到 PD 分离、vLLM 和服务部署架构；后半段翻到训练侧，讲显存为什么会爆、模型怎么切到几千张卡上、卡和卡之间怎么通信。

# 一、一次推理到底发生了什么

用户输进来的是一句自然语言，模型没法直接吃文本。所以第一步是 **tokenize**，把文本切成一串 token id；再过 **embedding** 把每个 token 变成向量；模型对这些向量做一通计算，最后吐出「下一个 token 的概率分布」，从里面采样出下一个词。如此循环，一个字一个字往外蹦。

这个生成过程分成两个阶段，**Prefill** 和 **Decode**。理解这两个阶段的差异，是理解后面一切的地基。

## Prefill：把 prompt 一次性嚼完

Prefill 阶段，模型把你输入的整个 prompt 的所有 token **一次性、并行地**处理一遍，算出每个位置的 attention，生成 KV Cache（待会儿解释这是什么），同时吐出第一个 token。

这个阶段的瓶颈是**算力**。因为所有 token 能并行算，GPU 的矩阵乘单元能吃得很满，利用率高。它对应的核心指标是 **TTFT**（Time To First Token，首 token 延迟）——你按下回车到屏幕上蹦出第一个字的时间。

## Decode：一个字一个字往外蹦

Decode 阶段是**自回归**的：一次只能生成一个 token，而且下一个 token 依赖上一个，所以**没法并行**。

这个阶段的瓶颈是**显存带宽**。原因很反直觉：每生成一个 token，都要把整个 KV Cache 从显存里完整读一遍，但实际上只算了一个 token 的量——**读得多、算得少**，所以卡在带宽上，不是算力。这时候 GPU 那些昂贵的矩阵乘单元其实大量闲置。它对应的指标是 **TPOT**（Time Per Output Token，每个输出 token 的延迟）。

:::note
**Prefill 能并行，所以算力 bound、利用率高**  
**Decode 不能并行，所以带宽 bound、利用率低**  
这也是后面 PD 分离的根本动机。
:::

## KV Cache：到底缓存了什么

先纠正一个常见错误：KV Cache 存的**不是激活值**（激活值是训练显存里的概念，后面会讲）。它存的是 **K 向量和 V 向量**。

在 attention 里，每个 token 都要算出三个向量：Q、K、V。当模型生成第 N 个 token 时，它的 Q 要去和**前面所有 token** 的 K、V 做注意力计算。

问题来了：如果不缓存，每生成一个新 token，都得把前面所有 token 的 K、V 重新算一遍，重复计算量会爆炸式增长。所以我们把每个 token 算过的 K、V 存下来——这就是 KV Cache。新 token 来了，只算它自己的 K、V，追加进缓存，再去读全部历史的 KV。

这一个机制顺带解释了两件事：

1. **为什么 Decode 是带宽 bound**：因为每生成一步，都要把整个 KV Cache 读一遍。
2. **为什么长上下文这么贵**：每生成一个 token 就往缓存里追加一组 K、V，上下文越长，KV Cache 越大，越吃显存。这就是长文本成本高的根源。

记住 KV Cache 这个东西——接下来要讲的 PD 分离和 vLLM，都是围着它转的。

# 二、PD 分离：把两个阶段拆开

P 是 Prefill，D 是 Decode。**PD 分离**就是把这两个阶段拆到不同的 GPU 集群上分别处理。

为什么要这么折腾？有两层原因。

## 第一层：两个阶段的资源画像根本不同

前面说了，Prefill 是算力密集的，需要高算力的卡；Decode 是带宽密集的，需要高显存带宽的卡。如果把它们混在一起跑，到了 Decode 阶段，那些昂贵的 Tensor Core 基本就在 idle，GPU 怎么都跑不满。

## 第二层：互相阻塞，而且 SLO 不同

这一层更微妙。Prefill 是个「大块头」任务，一次要算几千个 token；Decode 是无数个「小碎步」，一次就一个 token。

混部的时候，一个长 prompt 的 Prefill 进来，会把正在 Decode 的那一批用户全卡住，导致他们的 TPOT 出现毛刺——你正聊得好好的，突然卡顿一下，多半就是后台进来了个大 Prefill。

而且这两个阶段看的 SLO 指标压根不一样：Prefill 看 TTFT，Decode 看 TPOT。混在一起，根本没法分别优化，还互相抢资源。

:::tip
收口一句：PD 混部会让大块的 Prefill 阻塞细碎的 Decode，两阶段的 SLO 和资源画像都不同。拆开，才能各自独立组 batch、独立扩缩容、独立选卡型。
:::

## 代价：KV Cache 得搬家

PD 分离不是白拆的，它有代价——而这个代价，恰恰是「看过博客」和「真懂」的分水岭。

代价是：**得传 KV Cache**。Prefill 集群算完，生成的 KV Cache 可能有好几个 GB，得搬到 Decode 集群去接着干活。跨节点搬这么大的数据，只能靠 IB（InfiniBand）或者 RDMA 这种高速网络。搬得慢的话，前面省下来的时间又赔回去了。

所以工程上还得让**传输和计算重叠**——边传边算，不能干等传完再开始 Decode，否则 TTFT 会被活活拖长。

:::important
NVLink 和 IB 别搞混，这是高频混淆点：
- **NVLink** 管**机内**：同一台机器里 GPU 卡和卡之间的直连。
- **IB / RDMA** 管**机间**：跨节点、跨机器。

PD 分离里，Prefill 到 Decode 通常是跨节点的，所以走 IB / RDMA。
:::

# 三、vLLM：把 GPU 喂满的两把刷子

[vLLM](https://github.com/vllm-project/vllm) 是目前最主流的高吞吐 LLM 推理框架。它有两个杀手锏：**PagedAttention** 和 **Continuous Batching**。这俩配合起来，就是它吞吐高的核心原因。

## PagedAttention：借了操作系统的分页机制

这东西的思路，其实是直接借鉴了操作系统**虚拟内存的分页**（注意是分页，不是多级缓存）。

它解决的痛点是这样：传统做法会给每个请求**预留一整块连续的显存**来装 KV Cache，而且是按「最大可能长度」预留的。但用户实际生成的长度千差万别——我给你预留了 2048 个 token 的空间，结果你只生成了 100 个，剩下的全浪费了。

结果就是显存碎片化 + 过度预留，导致**实际能跑的并发数，远远低于显存理论上能支持的上限**。

PagedAttention 的做法是：把 KV Cache 切成一个个固定大小的小块（block），物理上不需要连续，用多少给多少，按需分配，用完回收。碎片基本消除，同样的显存能装下多得多的并发请求，吞吐量直接上去了。

:::note
一句话锚定：**PagedAttention 就是把「显存管 KV Cache」做成「操作系统管内存分页」。**

操作系统的分页解决的是物理内存容量不足和碎片问题，让程序能用比物理内存更大的虚拟空间；PagedAttention 解决的是 KV Cache 显存的碎片和过度预留问题。同一个思想，换了个战场。
:::

## Continuous Batching：逐 step 动态拼车

先说清楚一个 batch 里装的是什么。它装的**不是一堆 token，是 N 个并行的请求**，每个请求是一段独立的对话。GPU 把这 N 个请求并排放在一起，一次 forward 同时为每个请求各算出它们各自的下一个 token。

为什么要并排?因为 GPU 算 1 个请求和算 32 个请求，耗时其实差不多——这是矩阵乘的并行红利，不把它喂满就是纯浪费。

传统的 **static batching** 有个毛病：一个 batch 里的请求必须**一起开始、一起结束**。但每个请求生成长度不一样，短的早早算完了，却得干等着 batch 里最长的那个跑完，它的槽位空在那儿，GPU 就在空转。而且新来的请求得等整批结束才能组下一批，新用户的 TTFT 被白白拖长。

**Continuous Batching** 把调度粒度降到了**每一步 forward**：每跑完一步，谁生成完了就立刻让它「下车」，释放槽位和 KV Cache；等待队列里有新请求，就立刻让它「上车」，补进空出来的位置。所以这个 batch 的成员是逐步动态流动的，GPU 的槽位时刻保持满载。

:::tip
打个比方：static batching 是「快的请求被迫陪最慢的那个跑完，中途不能换人」；Continuous Batching 是「逐 step 动态拼车，完成的下车、新请求补位，绝不让 GPU 等最慢的那个」。

（顺带一提，它跟 pipeline 流水线没关系，别搞混。）
:::

## 两者怎么配合

Continuous Batching 想塞更多请求进来提并发，但显存是瓶颈；PagedAttention 把显存用得更省。一个负责**多拉客**，一个负责**省空间多装人**，合起来就是 vLLM 的高吞吐。

# 四、大模型服务部署架构

把上面的东西放进一个真实的线上服务里，完整链路长这样：

```
用户客户端
   ↓
API Gateway（网关）        ← 认证、限流、路由入口
   ↓
Load Balancer（负载均衡）   ← 把请求摊到多个后端实例
   ↓
Model Router（模型路由）    ← 大模型特有：该用哪个模型 / 哪个集群
   ↓
Scheduler（调度器）         ← 大模型特有：排队、组 batch、挑 GPU 实例
   ↓
vLLM 推理实例（GPU 上）     ← Continuous Batching / PagedAttention 在这层
   ↓
GPU（PD 分离：Prefill 集群 →[KV Cache 经 IB/RDMA]→ Decode 集群）
```

普通后端服务一般就是「网关 → 负载均衡 → 服务实例」三段。大模型服务在中间多了两层**特有**的东西：**Model Router** 和 **Scheduler**。原因很简单——GPU 又贵又稀缺，必须有专门一层做精细化调度，把利用率拉满。

走一遍这条链路：

请求进来，先到 **API Gateway**，做统一入口，负责认证、限流。然后到 **Load Balancer**，把流量摊到多个后端 vLLM 实例上，这一层本质跟 K8s 的 Service 是一回事。

接下来是两层大模型特有的：

- **Model Router**：决定这个请求该用哪个模型——按 API 里显式指定的字段、按租户、按版本灰度、或者按成本（简单请求给小模型省钱）。
- **Scheduler**：最有意思的一层。它负责**排队**（GPU 很贵，不可能无限扩）；负责**组 batch**（把多个请求拼起来喂给 vLLM，这就接上了 Continuous Batching）；负责**挑实例**（哪个实例的 KV Cache 显存还装得下就发给谁）；如果是 PD 分离架构，它还要决定 Prefill 发哪个集群、Decode 发哪个集群。

再往下，就是 vLLM 实例真正干活，最后落到 GPU 上。

## 两个值得深挖的细节

**Router 怎么路由？是不是用一个模型来判断？**

通常**不用模型，是规则化的**。因为路由这一层必须极快极稳，塞个模型进去反而增加延迟、多一个故障点。规则一般就是看 API 里显式指定的 `model` 字段（最常见），或者按租户、版本灰度、prompt 长度来分。

那种「用小模型先判断请求难度、再决定发大模型还是小模型」的做法，叫**语义路由 / LLM Router**，是一种进阶优化，主要为了省钱，但会引入额外延迟，不是默认做法。

**Scheduler 调度依据什么指标？**

第一约束是 **KV Cache 显存余量**——这跟普通后端服务看 CPU、看 QPS 很不一样。

为什么专门盯 KV Cache 显存?因为在一个 vLLM 实例里：算力通常有富余（Decode 本来就是带宽 bound）；权重占的显存加载完就固定了，不随请求变；**唯独 KV Cache 这块显存是随请求动态涨的**，每接一个请求、每生成一个 token 都在吃它。

显存是一堵硬墙，满了就直接 OOM 或拒绝服务，而算力还能挤一挤。所以调度器必须先确认这个实例的 KV Cache 池还装得下，才敢把请求发过去。

:::note
锚点：普通后端调度看 CPU / QPS，**LLM 调度第一看 KV Cache 显存余量**，因为显存是硬墙、满了就 OOM，算力反而常有富余。
:::

# 五、想让推理更快，从哪下手

如果有人问你「想做个更快的模型，怎么优化」，别张口就答「换好卡」——那是堆钱不是技术。可以分三层来讲。

## 第一层：模型层，减少计算量

- **量化**：把 FP16 降到 INT8、FP8 甚至 INT4，权重和激活都用更低精度，显存占用和带宽需求都降下来。对带宽 bound 的 Decode 直接提速。
- **MoE（混合专家）**：每次只激活部分专家，让**算力和参数量解耦**——参数量能做大，但单次推理的算力不涨。
- **投机解码（Speculative Decoding）**：用一个小模型先猜几个 token，大模型一次性并行验证。相当于把 Decode 那个「一次只能出一个 token」变成「一次验证好几个」，**直接绕开了 Decode 不能并行的死穴**。这是目前最热的 Decode 加速手段。

## 第二层：计算层，让同样的计算算得更快

- **FlashAttention**：把 attention 计算融合起来，减少显存和 SRAM 之间反复搬数据，既加速又省显存。
- **算子融合、CUDA Graph**：减少 kernel 启动开销。

## 第三层：服务层，把 GPU 喂满提吞吐

就是前面讲过的 Continuous Batching、PagedAttention、PD 分离。

:::tip
收口：从**减计算量、加速计算、提吞吐**三层下手。Decode 是带宽 bound，所以**投机解码和量化对它最对症**。
:::

# 六、训练显存：为什么 70B 模型单卡放不下

训练的时候，显存主要被四样东西占掉：**参数、梯度、优化器状态、激活值**。前三样是固定的，能现场算；第四样比较特殊。

## 现场算前三样：每参数 16 bytes

以 BF16 混合精度 + Adam 优化器为例：

| 项目 | 精度 | 字节/参数 |
|---|---|---|
| 参数本身 | BF16 | 2 |
| 梯度 | BF16 | 2 |
| 优化器状态·参数副本 | FP32 | 4 |
| 优化器状态·一阶矩 (m) | FP32 | 4 |
| 优化器状态·二阶矩 (v) | FP32 | 4 |
| **合计** | | **16** |

所以前三样合计**每个参数 16 字节**。一个 70B 的模型就是 `70B × 16 ≈ 1.12 TB`——远远超过单卡容量，H100 也才 80GB。

:::note
这是经典的「**Adam 训练每参数 16 bytes**」黄金公式。正因为 1.12TB 单卡放不下，才必须把模型切到多卡上去——这是后面所有分布式并行策略的起点。
:::

## 第四样：激活值，最大也最不可控

激活值是前向传播时每一层的中间输出，反向传播算梯度时要用到，所以得存着。

它跟前三样的区别在于：前三样只跟模型大小有关，是固定的；**激活值的大小还要看 `batch size × 序列长度 × 层数`**。batch 越大、序列越长，它越爆炸，所以它往往是显存里最大、最不可控的一块。

对应的优化技术叫**激活重计算（Activation Recomputation）**：前向时不全存激活值，反向需要的时候重新算一遍，用算力换显存。

# 七、分布式训练：模型怎么切到几千张卡上

既然单卡放不下，就得切。切法主要有四种思路：DP、TP、PP、ZeRO。

## DP（数据并行）：注意，它不省显存

每张卡放一份**完整的模型副本**，各喂 1/N 的数据并行算，算完用 **AllReduce** 把所有卡的梯度求平均、同步回每张卡，再各自更新，保证副本一致。

这里有个关键陷阱：**DP 解决的是吞吐、是加速，它不解决显存问题**。因为每张卡都得放完整副本，如果单卡本来就放不下整个模型，你开 100 张卡做 DP 照样 OOM。

## ZeRO：专门来补 DP 的显存冗余

ZeRO 的洞察是：DP 里每张卡都存一份完整的参数、梯度、优化器状态，这是巨大的冗余——100 张卡存了 100 份一模一样的优化器状态。

ZeRO 就把这三样**分片**到各张卡上，用到的时候再去要。它分三级：

- **ZeRO-1**：切优化器状态（最大的一块，性价比最高）。
- **ZeRO-2**：再加上切梯度。
- **ZeRO-3**：连参数本身也切，省得最狠，但每次前向反向都要临时从别的卡把参数收集回来，通信开销最大。

本质就是**用通信换显存**，让 DP 也能训练放不下的大模型。

:::important
ZeRO-3 和 TP 都切参数，区别是：**ZeRO 切完，用的时候会还原成完整的层来算**，逻辑上还是 DP；**TP 是把单层矩阵切开、就地分布式算，从不还原**。
:::

## TP（张量并行）：切宽

把单层里的大矩阵乘切开，比如一个权重矩阵按列切，多张卡各算一部分再拼起来。它**通信极其频繁**，每一层都要同步，所以一般只在**单机内多卡**用，走 NVLink 高速互联。它解决的是「单层都放不下」的情况——是**切宽**。

## PP（流水线并行）：切深

把模型按层切成几段：卡 1 管前 10 层，卡 2 管接下来 10 层，数据像流水线一样流过去。它的难点是**流水线气泡**——后面的卡要等前面的卡算完才有活干，中间会空闲。靠把数据切成 micro-batch 来填满流水线缓解。它解决的是「模型太深、层数太多放不下」——是**切深**。

:::tip
真正训超大模型是三者组合，叫 **3D 并行**：TP 切单层走机内 NVLink，PP 切层段走机间，DP / ZeRO 复制并行来扩吞吐。

一句话记牢：**TP 切宽、PP 切深、DP 复制扩吞吐、ZeRO 去 DP 冗余。**
:::

# 八、GPU 通信：并行策略本质是按带宽层级摆

切到几千张卡之后，卡和卡之间怎么高效交换数据，就成了新瓶颈。

## NCCL 是什么

NCCL（NVIDIA Collective Communication Library）是英伟达的 **GPU** 集合通信库，负责多 GPU、多节点之间高效交换数据。它会屏蔽底层差异：同机多卡走 NVLink，跨机多卡走 IB / RDMA。上层的 PyTorch 只管调 `AllReduce`，NCCL 自己选最优路径。

## AllReduce 与 Ring AllReduce

AllReduce 是 DP 同步梯度的方式：把所有卡的梯度求和或求平均，再同步回每一张卡。

具体实现一般用 **Ring AllReduce**（环形全规约）：把所有卡组成一个环，每张卡只和相邻的两张通信，数据分成块沿着环传递、边传边加。好处是**每张卡的通信量恒定、跟卡数无关**，所以能完美扩展到几千卡。如果用朴素做法——所有卡发给一张主卡汇总——主卡的带宽立刻成瓶颈。

## 三层通信带宽

```
卡内                ── 最快
卡间(同机)  NVLink   ── 很快（几百 GB/s）  → 所以 TP 放机内
机间        IB/RDMA  ── 快但比 NVLink 慢   → 所以 PP/DP 跨机
跨集群      普通以太网 ── 最慢              → 尽量不跨
```

这里是把分布式训练和 GPU 通信彻底打通的一句话：**并行策略怎么摆，本质是按通信频率去匹配带宽层级。** TP 每一层都要通信、最频繁，所以必须放在机内走 NVLink；PP 和 DP 通信频率低，就能容忍机间 IB 的延迟。

:::note
顺带记一个排障弹药——「训练卡在 99% / GPU 利用率低」通常三个原因：
1. **慢节点**：某张卡或某条链路慢，AllReduce 要等最慢的，全员卡住。
2. **通信瓶颈**：网络带宽不够或 IB 配置问题，计算在等通信。
3. **数据加载**：存储 IO 跟不上，GPU 在等数据。
:::

# 写在最后

把这一整圈捋下来，我最大的感受是：大模型工程里没有「为了炫技而存在的设计」。

- KV Cache 越来越大 → 所以有了 PagedAttention。
- Decode 带宽 bound、Prefill 算力 bound → 所以有了 PD 分离。
- GPU 槽位会空转 → 所以有了 Continuous Batching。
- 70B 模型 1.12TB 单卡放不下 → 所以有了 TP / PP / ZeRO。
- 几千卡之间通信会成瓶颈 → 所以并行策略要按带宽层级摆。

每一个术语背后，都是在跟**算力、显存、带宽**这三堵墙较劲。抓住这条主线，再看任何新框架、新论文，都能很快定位它到底在解决哪堵墙的问题。
